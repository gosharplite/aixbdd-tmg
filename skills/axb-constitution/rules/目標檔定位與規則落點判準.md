# Rule 1 - 根憲法只承接治理邊界，不承接 artifact 細則

- Level: `MUST`
- `CONSTITUTION.md` 只負責定義治理原則、讀取順序、目錄約定與規則格式邊界。
- 若需求是在描述某個 skill 的某個 artifact 應具備什麼欄位、語意、禁止事項或 example，
  不得寫進 `CONSTITUTION.md`。
- 若把 artifact 細則寫進根憲法，會讓根檔快速膨脹，破壞模組化設計。

## Good Example

- 這個例子是好的，因為根憲法只保留治理層資訊。

````md
### V. 目錄只保留真正會被讀的規則

1. `CONSTITUTION.md`
2. `shared.md`
3. `skills/<current-skill>/<artifact>.md`
````

## Bad Example

- 這個例子是壞的，因為它把 API response 細節直接塞進根憲法。

````md
### VI. API Response Rules

- 所有 `200` response 都必須包含 `roomId`
- 所有 `409` response 都必須包含 `errorCode`
````

# Rule 2 - 只有真正跨 skill 的規則才寫入 shared.md

- Level: `MUST`
- `shared.md` 只能收錄跨多個 skill 與多種 artifact 都會重複使用的規則。
- 若某條規則其實只服務單一 skill 或單一 artifact，應寫進 `skills/<skill>/<artifact>.md`。
- 判斷時以「誰會直接消費這條規則」為準，而不是以規則主題看起來是否通用為準。

## Good Example

- 這個例子是好的，因為語言一致性會被多種 artifact 共同使用。

````md
## Rule 1 - 說明文字必須使用繁體中文
````

## Bad Example

- 這個例子是壞的，因為 API response 其實只會由 `/axb-api-plan` 的 contract artifact 使用。

````md
## Rule 2 - 成功與失敗回應必須分流表達
````

# Rule 3 - skill 規則檔以 artifact 為最小落點

- Level: `MUST`
- `skills/<skill>/` 底下每一個 `.md` 檔都只處理單一 artifact。
- 若同一 skill 會產出 `spec.md` 與 `requirements-checklist.md`，應拆成兩個檔案，而不是混寫。
- 只有當兩條規則同時約束同一個 artifact 時，才應放在同一檔案中。

## Good Example

- 這個例子是好的，因為 skill 目錄下每個檔只對應一個 artifact。

````text
skills/axb-specify/spec.md
skills/axb-specify/requirements-checklist.md
````

## Bad Example

- 這個例子是壞的，因為不同 artifact 的規則被混在同一份檔案中。

````text
skills/axb-specify/constitution.md
# 內含 spec 與 requirements-checklist 的全部規則
````

# Rule 4 - 共用憲法必須承接 Claim→Witness 義務與專案決策面宣告

- Level: `MUST`
- 「未經見證之規範性宣稱絕不得晉升為 truth（Claim→Witness Obligation）」屬於跨越所有 skill、所有 phase 與所有 artifact 的最高治理原則，必須落點於專案的共用憲法 `.agents/constitution/shared.md`。
- 專案的 `.agents/constitution/shared.md` 必須明示宣告該專案的**決策面落點**（例如專案 ADR 目錄 `decisions/NNNN-*.md`）。未建立自動化見證之規範性宣稱屬於架構決策，必須於該宣告之決策面完成記錄（含理由、反洗白階梯審查與人類決策者拍板），絕不得以散文形式留存於任何 truth 表面。
- 若專案未宣告決策面落點，Claim→Witness 義務在遇到 `accepted-unwitnessed` 時應條件式阻擋（block conditionally），直到專案完成宣告為止。

## Good Example

- 這個例子是好的，因為共用憲法清楚定義了跨 skill 的 Claim→Witness 治理原則與專案決策面落點。

````md
## Rule X - 規範性宣稱未經見證不得晉升為 Truth (Claim→Witness Obligation)

- 任何規範性條目（FR / NFR / SC / EC）或系統行為保證，必須具備可執行之否證見證（可觀察者由 Gherkin BDD 承接，不可觀察者由 [WITNESS] 單元/故障注入 pin 承接），否則不得以散文形式作為 truth 存在。
- 若經階梯審查確屬無法自動化見證之決策，必須記錄於本專案之決策面：`decisions/NNNN-*.md`，並經人類決策者核可。
- 未經見證且未在決策面記錄之宣稱，嚴禁出現在任何 specs/truth/** 表面。
````

## Bad Example

- 這個例子是壞的，因為把全域適用的見證義務只當作單一 skill（如 axb-tasks）的局部細則，導致其他 truth owner 產生未受保護的散文真實。

````md
### 只有 axb-tasks 要檢查見證，其他 skill 可以自由在 techstack.md 或 dsl.md 寫入未見證保證。
````
