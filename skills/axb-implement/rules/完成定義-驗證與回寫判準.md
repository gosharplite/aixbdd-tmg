# Rule 1 - task 只有在實作與對應驗證都完成後才算完成

- Level: `MUST`
- 單一 task 的完成條件至少包含：所需變更已實作、對應檔案已寫入、且已完成與該 task 直接相關的驗證。
- 驗證方式應依 task 類型收斂，例如 targeted tests、lint、型別檢查、手動流程驗證、契約對照或啟動檢查。
- 不得把「程式已寫完但還沒驗證」視為已完成。

## Good Example

- 這個例子是好的，因為它把實作與驗證都跑完後才認定 task 完成。

```md
agent 完成 `roomStore.js` 的修改後，接著跑對應測試與啟動檢查。
確認驗證通過後，才把該 task 視為完成。
```

## Bad Example

- 這個例子是壞的，因為它只完成了程式修改，卻沒有任何完成證據。

```md
agent 寫完 `gameHandler.js` 後就直接說「這個 task 已完成」，但沒有跑任何測試、lint 或契約對照。
```

# Rule 2 - task 完成後必須立即回寫 `[X]`，且不得提前打勾

- Level: `MUST`
- 當且僅當 task 的實作與驗證都完成時，才可將對應 task 從 `- [ ]` 改寫為 `- [X]`。
- 不得先為了追蹤方便而預先打勾，也不得把同一批次中尚未驗證的其他 task 一起改成完成。
- 回寫時只修改實際完成的 task，保留其他未完成 task 狀態不變。

## Good Example

- 這個例子是好的，因為它只在完成條件成立後更新單一 task 狀態。

```md
agent 完成並驗證 `T014`。
它只把 `T014` 改成 `[X]`，而 `T015` 與 `T016` 仍維持 `[ ]`。
```

## Bad Example

- 這個例子是壞的，因為它提早打勾，讓 `tasks.md` 失去作為執行控制平面的可信度。

```md
agent 剛開始修改 `T014` 時就先把它改成 `[X]`，想說等全部做完再補驗證。
```

# Rule 3 - 完成回報應留下可追蹤的驗證證據與下一步狀態

- Level: `SHOULD`
- 每輪完成回報應說明：完成了哪些 task、做了哪些驗證、是否補強 repo hygiene、下一個已解鎖 task 是什麼或為何暫停。
- 回報應聚焦執行狀態與關鍵決策，不需要把所有細節寫成冗長 changelog。

## Good Example

- 這個例子是好的，因為它讓使用者能快速知道完成面、證據與 One-Shot 下一筆。

```md
已完成 `T001`、`T002`。
驗證：前後端 workspace 安裝與啟動腳本檢查通過。
已補強 `.gitignore`。
下一個已解鎖 task：`T003`。
```

## Bad Example

- 這個例子是壞的，因為它只說做完了，卻沒有留下驗證或 One-Shot 下一筆。

```md
今天完成很多東西，應該差不多可以用了。
```

# Rule 4 - Setup、Foundational、Phase 3 與 Feature 使用不同完成條件

- Level: `MUST`
- Setup 完成條件是：該則寫明的套件與配置已在，且 smoke-test 證明連得上。不得要求本輪 Feature 全綠，也不得把送訊語意寫進 Setup。
- Foundational 完成條件是：該則「只做」的實作程式、測試共用元件、入口、fixture、helper 或落點骨架已在，且沒有越過「不做」。不得要求 DSL 語意已對齊，也不得要求產品碼已綠。
- Phase 3 的 `[BDD-ALIGN]` / `[BDD-REMOVE]` / `[BDD-RED]` 完成條件是：該句測試語意已對齊 `dsl.md` 的 `StepDef 實作語意`，且可被跑到；失敗只能是 assertion 或產品行為，不能是 undefined step。不得要求產品碼已綠。
- Phase 3 review 完成條件是：本輪所有 Feature phase 的 `Test Scope` 跑起來沒有 undefined step；review subagent 沒有任何 issues。
- `[BDD-GREEN]` 完成條件是該 phase 的 `Test Scope` 全綠。
- `[CODE-REMOVE]` / `[REGRESSION]` 完成條件是過期產品行為已移除，且 `Test Scope` 通過、舊行為沒有被測試繼續保護。
- `[WITNESS]` 完成條件見 Rule 5：必須證明鑑別性突變能引發歸因明確之紅燈，且還原後測試重新全綠；或徹底自 truth 表面降級撤除散文並在專案決策面記錄。
- 不得因為新增測試通過，就把仍保護舊 truth 的測試留在程式碼中並回寫 `[X]`。

## Good Example

- 這個例子是好的，因為 Setup 停在連得上，Phase 3 停在可跑的紅燈，Green 才要求全綠。

```md
完成 T003 前：`websockets.connect` 能連上 FastAPI `/ws`。
完成 T004 前：`chat_helpers.py` 有函式殼，沒有各句 stepdef。
完成 T012 [BDD-RED] 前：空白送出 stepdef 已寫，跑得到 assertion failure。
完成 T015 review 前：本輪三個 Test Scope 都沒有 undefined step。
完成 T016 [BDD-GREEN] 前：`單人等待與空白訊息拒絕.feature` 全綠。
```

## Bad Example

- 這個例子是壞的，因為它要求 Phase 3 ALIGN 時 focused tests 就全綠。

```md
T008 [BDD-ALIGN] 還沒寫產品碼，測試仍紅，agent 拒絕回寫，卡死。
```

# Rule 5 - [WITNESS] 任務的完成定義（DoD）必須證明鑑別性反證與失敗歸因

- Level: `MUST`
- `[WITNESS]` 任務負責見證不可由 Gherkin 外部觀察之規範性條目（NFR / SC / EC / 內部不變量）。其完成條件（DoD）必須嚴格滿足下列三道關卡：
  1. **鑑別性突變（Discriminating Mutation）**：
     - 必須對被見證的保證機制實施單點突變破壞（例如：宣稱 fsync 耐久性時註解 `f.Sync()`；宣稱原子性替換時改為原地覆寫）；該突變必須使 `Test Scope` 內的測試轉為失敗（紅燈）。
     - 若突變後測試依然為綠，表示測試無鑑別力（non-discriminating），不具保護效力，不得視為完成。每項原子效果宣稱必須至少有一個鑑別性突變。
  2. **失敗歸因明確（Attributed Failure）**：
     - 測試失敗的原因必須直接且明確歸因於該被突變破壞的保證機制（符合預期之 failure shape / assertion failure），不得是由不相關的語法錯誤、未引用模組、環境掛掉或不相關之 panic 遮蔽。
  3. **還原重驗全綠（Revert-and-re-green）**：
     - 將突變破壞還原為正常實作碼後，重新執行 `Test Scope`，測試必須重新全數轉綠通過。
- **終端結果與降級處理（Terminal Outcomes & Demotion）**：
  - 成功完成上述三關者，始得回寫 `[X]`。
  - 若實施過程中發現該宣稱在當前環境下技術上無法建立自動化見證：**嚴禁假裝通過或提前打勾**。
  - 唯一合法的替代終端路徑為「**降級（Demote）**」：
    1. 將該保證自本輪所有 truth 表面（`specs/truth/techstack.md`、`dsl.md` 序言、DBML 註解等）徹底刪除散文，不得遺留任何未經見證之肯定句；
    2. 向人類決策者提報，由專案宣告之決策面（如專案 ADR）記錄為決策或 `accepted-unwitnessed`；
    3. 只有在 truth 散文全數撤除且決策面已完成記錄後，該 task 始得標記為降級關閉並回寫 `[X]`。
- 未完成鑑別性見證且未完成降級手續者，嚴禁回寫 `[X]`。

## Good Example

- 這個例子是好的，因為完整走完鑑別性突變、歸因確認與還原重綠。

```md
T015 [WITNESS] 回滾操作具原子性，崩潰不留殘留暫存檔
1. 實作單元測試 rollback_test.go::TestRollback_AtomicCrashSafety
2. 進行鑑別性突變：將 tempfile + rename 改為直接 truncate 寫入原檔
3. 執行測試：TestRollback_AtomicCrashSafety 失敗，報錯「舊歷史檔遭破壞」，失敗歸因明確
4. 還原實作碼並重跑：測試重新轉綠
5. 確認鑑別力具備，回寫 T015 為 [X]
```

## Bad Example

- 這個例子是壞的，因為測試從頭到尾只有綠燈，拔掉關鍵機制依然全綠，卻直接打勾。

```md
T015 [WITNESS] 回滾操作具備 fsync 落盤耐久性
agent 寫了一個測試只呼叫 Rollback()，看到 exit 0 全綠就打勾。
實際上把程式碼裡的 f.Sync() 註解掉，測試依然全綠——該測試根本無法見證 fsync 是否被呼叫。
```
