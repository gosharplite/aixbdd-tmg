# Rule 1 - `[P]` 是可平行許可；Parallel Hint 則是必須一次派出的批次

- Level: `MUST`
- 在 `/axb-implement` One-Shot 一輪恰好 1 個 task 的前提下，任務帶有 `[P]` 且沒有 `Parallel Hint` 時，只表示它在理論上可與其他 `[P]` task 平行，不表示必須綁成同一輪。
- 若當前 phase 有 `Parallel Hint`，必須依 `rules/ParallelHint平行Subagent與衝突Merge判準.md` 一次派出 Hint 列出的 `[P]` 批次。
- 未標 `[P]` 的序列 task 不得併批。Feature phase 預設序列。

## Good Example

- 這個例子是好的，因為 Feature Green 仍序列，Phase 3 則遵守 Hint。

```md
Phase 3 有 Parallel Hint：一次派出 T008–T014。
Phase 4A 的 T016 [BDD-GREEN] 與 T017 [BDD-REFACTOR] 未標 [P]，仍序列。
```

## Bad Example

- 這個例子是壞的，因為它看到 `[P]` 就無視 Hint 範圍，或把 Feature Green 也平行掉。

```md
把 T016 [BDD-GREEN] 與 T018 [BDD-GREEN] 一次平行改同一份 store。
```

# Rule 2 - 共享檔案時必須序列；Parallel Hint 平行派出以獨立檔案（Zero Shared Edits）為原則

- Level: `MUST`
- Feature phase 或非 Phase 3 的 task 若會修改同一檔案、同一模組責任邊界，或需要依賴同一份尚未穩定的驗證結果，必須序列執行。
- Phase 3 的 `[P]` 批次：
  - 若目標檔案彼此獨立（Zero Shared Edits 原則，一任務一檔案），必須依 `Parallel Hint` 一次派出整批 subagent 並行執行。
  - 若多個 `[P]` tasks 寫入同一實體檔案，為避免 Lost Update 寫入衝突，必須按目標檔案序列執行（前一個 task 寫入落盤後，後一個 task 讀取最新內容再疊加改動），不得讓多個 subagent 同時並行寫入同一實體檔案。細節以 `ParallelHint平行Subagent與衝突Merge判準.md` 為準。
- 當存在明確的整合 task 時，前置 task 完成後應由整合 task 收斂。

## Good Example

- 這個例子是好的，因為獨立檔案並行派出，共享檔案則安全序列。

```md
Phase 3 獨立檔案：T008 寫 `when_send.go`，T009 寫 `then_recv.go`，一次平行派出。
Phase 3 共享檔案：T008 與 T009 都寫 `操作與斷言.py`，orchestrator 序列執行（T008 落盤後 T009 才讀取最新內容並寫入）。
Phase 4 共享檔案：T016 與 T018 都改 `store.py`，序列執行。
```

## Bad Example

- 這個例子是壞的，因為明明各寫獨立檔案卻無視 Parallel Hint 硬改成序列，或明明寫同一檔卻盲目並行導致寫入覆蓋。

```md
T008–T011 各自寫入獨立檔案（如 `step_a.go`、`step_b.go`），且 Phase 3 有 Parallel Hint，卻無視平行許可硬改成一個一個做。
或者：T008 與 T009 寫同一個檔案，agent 仍同時並行派出兩個 subagent 改同檔，造成 Lost Update。
```

# Rule 3 - 平行批次完成後，應先各自驗證，再做整體收斂驗證

- Level: `SHOULD`
- 若本輪確實存在平行批次，應先確認每個 task 自己的局部完成條件，再做一次整體收斂驗證。
- 不應只驗證其中一個 task 就把整批視為完成。
- Phase 3 的整體收斂驗證由 review task 承擔。

## Good Example

- 這個例子是好的，因為它先看局部，再看 review。

```md
T008–T014 各自回報對齊結果後，T015 review 跑本輪所有 Test Scope，確認沒有 undefined step。
```

## Bad Example

- 這個例子是壞的，因為它只驗證其中一項就整批打勾。

```md
agent 只看了 T008 的 diff，就把 T008–T014 一起改成 `[X]`。
```
