# Rule 1 - `ui/ui-plan.md` 是控制平面，雛形是可 review 的產品表面

- Level: `MUST`
- 本判準同時涵蓋兩種 medium：web／`frontend` 的 HTML 雛形（`ui/*.html`），以及互動式 CLI 的 terminal 雛形（`ui/screens/*.txt`）。檔名沿用最初以 web 為範圍的命名；內容已一般化為兩種 medium。
- `axb-ui-plan` 的產出順序必須是先定稿 `ui/ui-plan.md`，再依這份 plan 產出對應 medium 的雛形。
- `ui/ui-plan.md` 的責任是整理介面範圍、medium、畫面與流程、狀態、驗證與雛形輸出規劃。
- web 雛形（`ui/*.html`）的責任是把上述 plan 落地成可點擊、可換頁、可感受產品節奏的高保真靜態雛形。
- terminal 雛形（`ui/screens/*.txt`）的責任是把上述 plan 落地成與終端實際渲染一致的框架；其可操作性由 `ui/ui-plan.md` 的 `Keybinding 對照表` 與 `狀態轉移清單` 承擔，讓 reviewer 能追蹤 key → state → outcome。
- 不可把控制平面與雛形混成一份產物，也不可讓雛形先成形後再倒推關鍵流程決策。

## Good Example

- 這個例子是好的，因為它先用 `ui-plan.md` 收斂畫面與 flow，再用多個雛形真正呈現產品。

```md
1. 先完成 `ui/ui-plan.md`
   - web：定義 `ui/index.html`、`ui/product-detail.html`、`ui/checkout.html`
   - terminal：定義 `ui/screens/entry.txt`、`ui/screens/10-suggestion.txt`、`ui/screens/20-running.txt`
   - 定義每個畫面的主要目的與轉移關係

2. 再依 plan 產出對應 medium 的雛形
   - web：`ui/index.html`、`ui/product-detail.html`、`ui/checkout.html`
   - terminal：`ui/screens/entry.txt`、`ui/screens/10-suggestion.txt`、`ui/screens/20-running.txt`
```

## Bad Example

- 這個例子是壞的，因為它先畫雛形，再回頭補 plan，導致單一溯源不成立。

```md
1. 先隨手做出三個 HTML，或三個終端框架
2. 後面再看要不要補 `ui/ui-plan.md`
3. 發現流程衝突時，再回頭改所有檔案
```

# Rule 2 - 雛形必須看起來像產品，不是說明文件

- Level: `MUST`
- web 雛形（`ui/*.html`）中只能放產品真的會顯示給使用者的內容，例如標題、欄位、狀態、CTA、錯誤訊息、結果摘要與假資料。
- terminal 雛形（`ui/screens/*.txt`）中只能放終端真的會渲染給使用者的框架內容，例如標題列、面板、欄位、游標、狀態列、錯誤列與假資料。
- 兩種 medium 都不可把分析備註、元件樹、實作 TODO、欄位解說、review 說明、`Keybinding 對照表` 或 `狀態轉移清單` 直接寫進雛形畫面。
- 若某段資訊是給開發者或 reviewer 看的，應留在 `ui/ui-plan.md`，而不是放進產品表面。

## Good Example

- 這個例子是好的，因為終端框架只呈現使用者真的會看到的產品內容，keybinding 對照表留在 plan。

```text
┌─ tell-me-go · 互動提示 ──────────────────────────────┐
│ 輸入你的問題，使用 ↑/↓ 瀏覽建議、Tab 接受建議         │
│                                                       │
│  輸入                              [編輯中]           │
│  deploy to staging                                   │
│  ▏                                                    │
│                                                       │
│  Enter 送出 · Tab 接受 · ? 說明 · Ctrl+C 取消         │
└───────────────────────────────────────────────────────┘
```

## Bad Example

- 這個例子是壞的，因為它把說明文件內容（keybinding 對照表、實作 TODO）直接塞進產品框架。

```text
┌─ 框架一：互動提示 ───────────────────────────────────┐
│ 本畫面主要目的是讓使用者輸入指令。                    │
│ Keybinding：Enter=送出、Tab=接受、?=說明              │
│ TODO: 之後這裡可能要改成真正的 TUI。                  │
└───────────────────────────────────────────────────────┘
```
